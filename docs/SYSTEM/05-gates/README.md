# Ворота: самообучение и любые изменения правил

Принцип: машина допускает, человек утверждает. Предлагать и оценивать кандидатов может любой механизм; продвигать — никто, кроме владельца.

1. Кандидат — один файл в `candidates/`: формулировка правила, примеры из пар «черновик → правка», какую метрику должно улучшить, ярус происхождения (из наблюдённого факта — продвигаемо; «по структуре» — только наблюдение), уверенность, доказательства. Правило из одной пары к воротам не допускается.
2. Контрольный набор заморожен (`frozen-sets/`, хеш); содержит элементы «не трогать» и «одна разрешённая правка».
3. Прогон: хеш кандидата и хеш рубрики фиксируются до прогона; метрики до/после на замороженном наборе; условие: ни одна метрика не хуже, факты 100 %, прирост статистически значим (минимум два прогона); судьи — если их больше одного — из разных семейств; расхождения поимённо; `NOT_RUN` там, где не меряли. Отчёт — `gate-reports/gate-NN.md`.
4. Прошедшие — в `approved-pending.md`; владелец ставит «да / нет» с датой; «нет» хранится с причиной и повторно не предлагается.
5. Внедрение — один коммит на одно правило со ссылкой на gate-NN; запись в `applied.md`.
6. Откат — одним коммитом, причина в `rollbacks.md`.
7. Раз в N пар случайное утверждённое правило перепроверяется на свежем наборе.
8. Автономные циклы «до критерия» допускаются только там, где критерий проверяет машина, с лимитом итераций и без коммитов; перед включением — проверка: цель машинно-решаема, границы заданы, судья независим, последний рубильник у человека.

Источник: humanizer2/CONTROL.md B; ARS MEASUREMENT_CONTRACT и revision_claim_drift; C-7.A №9; C-8.A №3–5 (flywheel-receipt, ярусы происхождения); ECC loop-design-check; решения владельца по Ralph Loop и GSD.
