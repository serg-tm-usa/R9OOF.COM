# pdf-visual · план дописки навыка `pdf-markitdown` визуальным поиском по сканам

> Статус: предложение чата R9OOF.COM (правило владельца 2026-10-05). Куда этот план отправить и что с ним делать в чате-получателе, указывает владелец.

Отдельный план по правилу владельца: своя папка, `PLAN.md` + `MEMORY.md` + `CONTROL.md`. Этот чат (R9OOF.COM) код не пишет; план передаётся проекту-исполнителю (чат «Заземление», владелец навыка `pdf-markitdown`).

Источник решения: `docs/ideas.md`, строка PixelRAG от 2026-10-05; слова владельца: «в заземлении у нас огромные базы сканированного текста»; «у нас есть скилл обработки PDF, думаю надо взять нужное и дописать наш».

## 1. Что есть сейчас

Навык `pdf-markitdown` v06 (синхронизированный навык владельца): лестница чтения markitdown → pdftotext → pdfplumber → pypdf → растр → tesseract; постраничные уровни достоверности A/B/D; классы листов `text / table / drawing / mixed / scan / empty`; индекс чертежей с растрами PNG; паспорт; таблицы; реестр величин; глоссарий CJK; сборка базы по `kb-protocol` (index + extract + drawing); контроль SHA-256.

Чего нет: поиска по базе **по виду листа**. Сейчас лист класса `scan` уровня D либо распознаётся tesseract (с известными отказами: «180 кН» → «180 KH»), либо «только растр, цитирование запрещено». Найти нужный лист среди тысяч сканов можно только по распознанному тексту, то есть с теми же ошибками.

## 2. Что берём из PixelRAG (StarTrail-org, Apache-2.0)

Не весь проект, а четыре вещи. Всё остальное (индекс Википедии на 217 ГБ, облачный API api.pixelrag.ai, обучение LoRA в `train/`, многопоточный рендер Chrome) — не берём.

| № | Из PixelRAG | Что это | Как ложится в `pdf-markitdown` |
| --- | --- | --- | --- |
| П1 | `pixelshot` / `render_pdf` (PyMuPDF) | PDF → плитки JPEG + манифест `tiles.json` (документ, лист, номер плитки, координаты) | у нас растр уже есть (`pdftoppm`, правило 3 и 5). Берём **форму манифеста**: один файл на документ со списком плиток, привязкой к листу и SHA-256 исходника. Сам `pixelshot` не обязателен |
| П2 | `pixelrag chunk` · `embed` · `build-index` | плитки → векторы моделью `Qwen/Qwen3-VL-Embedding-2B` → индекс FAISS; `device: auto` (cuda / mps / cpu) | новый необязательный этап **визуального индекса базы**: один индекс на базу знаний, не на документ. Тяжёлые зависимости (torch, transformers, faiss) ставятся отдельным окружением, навык вызывает их как внешнюю команду |
| П3 | `pixelrag serve` | поиск по индексу: вопрос текстом (или картинкой) → N плиток с оценкой | команда **поиска**: вопрос → список листов с оценкой, уровнем и путём к PNG → модель смотрит растры и отвечает. Только локально, 127.0.0.1 |
| П4 | принцип «ответ читается с картинки» | модель зрения читает найденную плитку, а не распознанный текст | совпадает с нашим правилом 3 «смотреть растр». Добавляет новый способ получить ответ с листа уровня D без OCR |

Отдельно, не в навык: плагин **pixelbrowse** (скриншот веб-страницы → модель читает картинку; без MCP и без сервера, вызывает `pixelshot` локально). Полезен «Заземлению» для чтения веб-источников с таблицами и графиками; проекту сайта — для просмотра страниц глазами. Решение по нему отдельное, после T-43 (сканирование SkillSpector).

## 3. Как это встраивается: правила навыка, которые меняются

- **Правило 2 (лестница).** Между «pdftoppm + просмотр глазами» и «tesseract» появляется ступень **визуальный поиск**: по вопросу находятся листы, модель читает их с растра. OCR остаётся последней ступенью и запускается только по правилу 7.
- **Правило 4 (уровни).** Лист уровня D, прочитанный моделью с растра по результату визуального поиска, получает уровень **B с пометкой «прочитано моделью с растра, лист N, плитка M»**. Числа, единицы и обозначения — только после второго взгляда на растр крупнее (как для OCR). Запрет «цитирование с D» сохраняется для непросмотренных листов.
- **Правило 5 (индекс чертежей).** Манифест плиток становится общим для `drawings` и для визуального индекса: один растр, одна привязка к листу.
- **Правило 8 (сборка базы).** К комплекту `index / extract / drawing` добавляется тип **`vindex`** (файлы индекса FAISS + манифест плиток + модель и её версия). Класс хранения P (библиотека), в рабочий проект попадает только запись в индексе: «визуальный индекс есть, дата, число листов». Имена — по `kb-protocol`, словарь типов дополнить.
- **Правило 8г (целостность).** Индекс хранит SHA-256 каждого исходника; при расхождении — лист помечается «индекс устарел», поиск по нему запрещён до пересборки. Пересборка только добавочная: новые и изменённые документы, не вся база.
- **Правило 9 (ссылка).** К ссылке добавляется: «найдено визуальным поиском, оценка 0,73, плитка 3 листа 12; прочитано с растра».
- **Правило 10 (ответ).** В ответе указывать, какие листы найдены визуально, какие прочитаны, какие нет.

Ни одно существующее правило не ослабляется: визуальный поиск добавляет способ **найти** лист и способ **прочитать** лист без OCR, но не отменяет сверку с растром.

## 5. Ограничения и риски (сверить с `risks.md` Humanizer 2 по форме)

1. **Железо.** Модель 2B на CPU: ожидать секунды на плитку; на базу в 100 000 листов — дни. Без GPU индексировать ночами порциями или брать меньшую модель (ColPali-варианты). Проверить на этапе 1, не предполагать.
2. **Русский язык и плохая печать.** Qwen3-VL многоязычная, но дообучена авторами на англоязычных скриншотах. Проверить на этапе 1 именно на наших сканах; таблицы с мелкими числами — отдельный тест.
3. **Загрузка модели.** ~4 ГБ с Hugging Face, один раз; хранить в библиотеке класса P с указанием версии, чтобы индекс и модель не разъехались (индекс одной модели не читается другой).
4. **Безопасность.** Всё локально: `serve` только на 127.0.0.1, облачный `api.pixelrag.ai` не использовать, сканы наружу не уходят. Пакет `pixelrag` с PyPI ставить после отчёта SkillSpector (правило 6 в `checks.md`); перезаливы репозитория (seco/, sp00ler/ и др.) не брать.
5. **Ложная уверенность.** Оценка поиска — не достоверность. Лист найден ≠ ответ верен; чтение с растра подчиняется правилу 4. В отчёте пробы считать отдельно «лист найден» и «ответ верен».
6. **Размер навыка.** Тяжёлые зависимости не в папку навыка: навык остаётся текстом и лёгкими скриптами, иначе синхронизация навыков ломается.
