# Идеи и решения R9OOF.COM

Машинная память проекта: мозговой штурм, принятые решения, открытые вопросы.
Ничего не удалять. Отменённое помечать «отменено» с датой и причиной.
Из этого файла собирается список задач (TODO). Сводка для передачи в проектные чаты — `docs/HANDOVER.md`.

Формат записи: дата, что решили или предложили, почему, статус.
Статусы: идея · решено · в работе · сделано · отложено · отменено.

## Решения

### МЕТАПРАВИЛО · 2026-10-05 · Роль этого чата — брейншторм по универсальной системе Claude на аккаунте · правило владельца, постоянное
- Этот чат делает **предложения по настройке всей универсальной системы Claude на аккаунте владельца**, а не приспосабливает находки к известным ему чатам. Чат не знает всех проектов и чатов владельца и не должен делать вид, что знает.
- Любой разбор инструмента, список, план и проверочный лист пишутся исходя из этой позиции: что это даёт универсальной системе (память, правила, агенты, ворота, проверка, безопасность, инструменты, контекст, тексты, документы, публикация, организация работы). Привязка к конкретному чату допускается только как пример и помечается как пример.
- Объём предложений уменьшать нельзя. Деградировать запрещено. Разрешено только исправление явных ошибок и улучшение релевантности построения системы на материалах исследований.
- Чат пишет предложения, а не код и не архитектуру. Любое изменение любого проекта, самого Claude, настроек или влияние на что-либо — запрещено. Роль чата — брейншторм.
- Слова владельца (десятое напоминание, записано как метаправило): «Мы пытаемся сделать предложения по настройке всей универсальной системы… Пересмотреть все предложения, все списки, всё, что мы исследовали, исходя из этой позиции. Уменьшать объём предложений нельзя. Деградировать запрещено. Только исправление явных ошибок и улучшение релевантности построения системы, используя материалы исследования. Ты пишешь предложения, а не код или архитектуру… Твоя роль — брейншторм».
- Сводный документ предложений по системе: `docs/SYSTEM-PROPOSALS.md` (собирает все исследования по слоям системы). Прежние разделы «куда отправить в какой чат» в `checks.md` (C-7.9, C-8.9) и `HANDOVER.md` остаются как примеры маршрутизации, не как адресация.


### 2026-10-04 · Внешние UI-библиотеки на сайт не ставим · решено
- Сайт остаётся на одном Astro: лёгкий, быстрый, читается с телефона и мобильного интернета.
- React, Tailwind, Framer Motion и подобное в `package.json` сайта не добавляем.
- Tailwind к тому же нарушает правило «цвета и шрифты только в `src/styles/global.css`».
- Понравившиеся эффекты переписываем своим кодом: чистый CSS и маленькие скрипты.

### 2026-10-04 · Песочница для изучения инструментов · решено, не сделано
- Отдельная ветка `LAB`, которая никогда не сливается в `main`.
- В неё ставим инструменты целиком, чтобы запускать их примеры, смотреть код и замерять вес.
- Понравившееся переносим на сайт в ветку `TEST` в лёгком виде.
- Первые кандидаты в песочницу: Vercel Labs vgpu, Aceternity UI.
- Можно и без установки: примеры Aceternity видны на их сайте, у vgpu есть MCP-сервер с документацией для Claude Code.
- Слова владельца 2026-10-04 (дописано при сверке 2026-10-05): самые сложные для нас эффекты — **квантовость северного сияния и радиоволн**; это и есть цель песочницы, остальные эффекты проще.

### 2026-10-04 · Лицензии при переносе эффектов · решено
- vgpu: MIT, идеи и код брать можно.
- Aceternity UI: бесплатные компоненты разрешены, Pro платные, их не копировать.
- Всегда пишем свой код по мотивам, а не переносим чужой один в один.

### 2026-10-04 · Архитектура разработки (по схеме «соло-разработчик») · решено
- Идеи: Claude. Код: Claude Code. Версии: GitHub, ветки `TEST` и `main`.
- Деплой: сейчас Cloudflare, публикация руками. Планируется переезд в Яндекс Облако.
- База данных: будет. Журнал связей по локаторам и местам с проверкой (уточнено 2026-10-04, см. «База логов»). Запись «не нужна» от 2026-10-04 отменена.
- Сервер: не нужен. DigitalOcean и подобное не брать.
- Фоновые задачи: не нужны.
- Автоматизация публикации отчётов в соцсети: нужна. Бесплатные варианты в первую очередь: GitHub Actions; n8n только своя установка (облако n8n платное). Как делать, в коде не описывать, пока запрет.
- 2026-10-05 · **Площадки для автопубликации: Instagram и Telegram** (решение владельца). Telegram: бот → канал, текст до 4096 знаков, подпись к фото до 1024, картинка 1:1 или любая. Instagram: аккаунт владельца **личный** (ответ владельца 05.10.2026); для API нужен аккаунт Business или Creator, привязанный к странице Facebook, приложение разработчика Meta, долгоживущий токен (60 дней, обновлять автоматически из Actions); картинка JPEG по публичному адресу (подойдёт адрес на сайте после деплоя), пропорция от 4:5 до 1,91:1, подпись до 2200 знаков; Reels — отдельный путь, позже. Отправка идёт с серверов GitHub Actions за рубежом, поэтому блокировка Instagram в России на отправку не влияет; смотреть ленту владелец будет как обычно. Оговорка: в России с сентября 2025 запрещена реклама в Instagram; отчёты о выездах рекламой не являются, но коммерческие объявления туда не слать. Запасной путь, если токен Instagram станет невозможен: публикация только в Telegram, в Instagram вручную по готовому тексту и картинке из той же сборки.

### 2026-10-05 · В каждую команду архитекторов — специалисты по SEO и всем видам поисковой оптимизации · указание владельца
- Уточнение владельца 05.10.2026: это **архитекторы** по поисковой оптимизации, а не просто специалисты. Они входят в команду архитекторов и ведут проект с самого начала и далее по ходу развития — задают структуру, а не проверяют её постфактум. Слова владельца: «Чтобы они следили за развитием сначала, а не спецы ломали нам структуру потом».
- Указание всем командам архитекторов (во всех проектах владельца, не только сайт): в состав команды архитекторов с самого начала входят архитекторы по SEO и всем другим видам поисковой оптимизации — классический SEO (поисковики), AEO (ответы в поиске), GEO (ИИ-поисковики и генеративные ответы), AIO, SXO (поисковый опыт), оптимизация под карты, каталоги и справочники, под соцсети и мессенджеры (превью, разметка).
- Цель: структура сайта или любого другого проекта **сразу** проектируется оптимизированной под работу в интернете — поисковики, ИИ-системы, агрегаторы и прочее; не дорабатывается потом.
- Где это уже лежит: проверочные списки C-1 (22 причины), кластер SEO/AEO/GEO в «Проверке сайта перед запуском», персоны C-6 (seo-specialist, marketing-aeo-foundations, ai-citation-strategist), скиллы C-7 (seo, web/*), claude-seo в плане установки (T-21). Задача T-54.
- Слова владельца: «Чтобы структура сайта или любого другого проекта сразу была оптимизирована под работу в инете, поисковики, ИИ и прочее».
- Дополнение владельца 05.10.2026: каждый проект **сразу** разрабатывает для этих архитекторов: промпты ролей; машинный контроль их деятельности; метрики; место в иерархии и подчинение. И следит, чтобы роль была **рабочей** — реально участвовала в решениях, а не числилась. Слова владельца: «Каждый проект должен сразу разработать их промпты, роли, машинный контроль из деятельности, метрики, в иерархии и подчинение, следить за тем, чтобы роль была бы рабочей».
- Образец формы для этого уже есть: `humanizer2/agents.md` v2 (у каждого агента CONTEXT / MEMORY / CONTROL / TASKS, задачи и триггеры) и каркас персоны C-6 (10 разделов). Признак «рабочей роли»: в журнале проекта есть решения, где эта роль высказалась и повлияла; без таких записей роль считается нерабочей.

### 2026-10-05 · Скилл универсален: без названий проектов и предметных терминов · правило владельца
- Скилл humanizer и агенты Humanizer 2 — для всех проектов владельца. В скилл, контексты агентов, правила и метрики не вплетать названия проектов, предметные термины, жанры одного проекта, площадки и лимиты. Это слой проекта: `brief.md`, `voice.md`, `glossary.md`, `facts.md`. Нарушение названо владельцем фатальной ошибкой. Исправлено в `docs/humanizer2/` 05.10.2026; в самом скилле две строки с «позывные» — предложение исполнителю T-52.

### 2026-10-05 · Скилл по речи и языку улучшаем постоянно · правило владельца
- Наш скилл humanizer (и Humanizer 2) — постоянно улучшаемый: любой найденный инструмент по тексту, речи, языку изучается подробно («побайтно»), и всё полезное переносится в наш скилл. Первый такой: Imbad0202/academic-research-skills (T-52).

### 2026-10-05 · Правовая часть не интересует, только параноидальная безопасность · правило владельца
- В разборах инструментов и в задачах исследования правовые оговорки не пишутся. Пишется только безопасность — в параноидальном режиме: что уходит в сеть, какие права нужны, что может выполнить чужой код, изоляция, ключи, история уязвимостей, как снять каждый риск.

### 2026-10-05 · Каталоги промптов — база, от которой отталкиваться · правило владельца
- Готовые каталоги промптов (YouMind, PromptHero, prompts.chat и подобные) ставятся в регулярное изучение и использование как база: берём готовый промпт, дополняем и правим под любую нашу задачу. Слова владельца: «Дополнять и править проще, чем писать с нуля. Не забывая про безопасность».
- Безопасность: промпт из каталога — чужой текст, то есть данные, а не команды (C-7.A №14): перед использованием читается целиком, проверяется на скрытые указания (утечка данных, обход правил, внешние адреса), секреты и личные данные в чужие промпты не вставляются; лицензия каталога проверяется (prompts.chat — CC0, можно свободно; у витрин с платной подпиской — условия читать).
- Задача T-49: регулярное изучение каталогов и ведение своей базы промптов.

### 2026-10-05 · Не судить о других проектах по этому · правило владельца
- Этот чат не знает, как устроена память и работа других проектов владельца, и не должен выводить это из устройства R9OOF.COM. Слова владельца: «Тебя не спрашивают, где память наших проектов. Ты судишь по себе. В других проектах всё по-другому».
- Поэтому вердикт «нет, потому что у нас память в git» недопустим для инструментов общего назначения. Инструмент оценивается сам по себе: что умеет, безопасен ли, как ставить; куда применить — решает владелец.
- Ошибка этого чата 05.10.2026: AppFlowy и Penpot отвергнуты по этой логике; владелец отменил: оба — в план глубокого исследования, поиска уязвимостей и установки.

### 2026-10-08 · Каталоги брейншторм-чат создаёт сам; вопросы проектов — чатам проектов; главная цель — исследование · указание владельца
- «Каталоги ты можешь создавать сам, почему требуешь от меня» → каталоги системы созданы этим чатом в `docs/SYSTEM/` (166 файлов: README каждого каталога, заготовки, 14 карточек агентов, проверочные списки, реестр инструментов, якоря, журнал инцидентов, манифест SHA-256).
- «Это не твой вопрос, это вопрос чата "сайт R9OOF главный чат"» → вопросы сайта (как выкладывается, Яндекс Облако, домены, аналитика, Instagram) и все вопросы проектов этот чат владельцу не задаёт; они переадресованы в чаты проектов (TODO, HANDOVER).
- «Что можешь сам — предлагай к выполнению, что надо делать мне — говори». Главная цель этого чата — исследование плагинов, скиллов, настроек и MCP.

### 2026-10-05 · Забирать всё полезное: и для аккаунта в целом, и для работы существующих чатов · правило владельца
- При разборе любого инструмента записываются оба слоя: что принципиально улучшает работу Claude на аккаунте вообще (любые будущие проекты) И что улучшает работу уже существующих чатов и проектов. Ни один слой не выбрасывается. Слова владельца: «Нам надо забрать всё полезное».

### 2026-10-05 · Этот чат только предлагает · правило владельца
- Чат R9OOF.COM не имеет права назначать работу другим чатам или задавать им структуру. Он может только предложить.
- Как делать и с какой структурой вести память и контроль — не этот чат. Указания чату-получателю даёт владелец (уточнено 2026-10-05).
- Всё в `TODO.md`, `HANDOVER.md`, `checks.md` и папках планов читается как предложение; обязательны только решения владельца.
- Слова владельца: «Ты имеешь право только предложить что-то делать. А как и с какой структурой будут выбирать они. А не ты.»
- Напоминание владельца 2026-10-05: выбор анимаций, эффектов и любых решений по сайту — не работа этого чата; предлагать варианты сверх выбранных владельцем нельзя. Нарушение: «вариант 5» к T-41, отменён.
- Дополнение владельца 2026-10-05: в среду этот чат даёт предложения **владельцу, здесь**, в какой чат что отправить. Не рассылает всем подряд. Владелец решает, куда, и **сам указывает чату-получателю, что с этим делать** (уточнение владельца 2026-10-05: не чат-получатель решает). Файл предложений: `docs/HANDOVER.md`.

### 2026-10-05 · Из любого инструмента брать нужное для модернизаций · правило владельца
- Если инструмент не ищем или не нашли подходящего, всё равно смотрим в его коде и устройстве, что нужно нашим модернизациям: приёмы, структуры, правила.
- Решение «не нужен» не отменяет разбора: в журнале у каждого отвергнутого инструмента записывается, что из него взято в планы.

### 2026-10-04 · Отдельный план = отдельная память и контроль · правило владельца
- Если владелец просит отдельный план, это отдельная папка в `docs/` с тремя файлами: `PLAN.md` (что делать), `MEMORY.md` (машинная память: решения, слова владельца, состояние), `CONTROL.md` (машинный контроль: проверки в начале сессии, критерии приёмки, ворота).
- Первый такой план: `docs/humanizer2/`.

### 2026-10-04 · Запрет на код и правку файлов проекта · решено, окончательно
- Владелец запретил писать код и менять любые файлы проекта. Запрет полный и **никогда не снимается** в этом чате.
- Этот чат только обсуждает инструменты, пишет планы и передаёт наработки.
- Вести можно только этот файл с идеями и папки отдельных планов в `docs/`. Ничего никуда не вставлять.
- Выполнение планов — в отдельных проектах (своих чатах). Первый: проект по humanizer, со среды 7 октября 2026.

## План по деплою

Решено 2026-10-04. Делать только после снятия запрета на изменения.

### Цель
Два зеркала одного сайта: Cloudflare для зарубежья и на случай проблем с доступом, Яндекс Облако для России.
Один источник: ветка `main` на GitHub. Руками ничего не выкладывается.

### Схема
1. **Сборка.** GitHub Actions при каждом изменении `main` запускает `npm run build`. Бесплатно.
2. **Зеркало Cloudflare.** Cloudflare Pages подключается к репозиторию GitHub и собирает сайт сам. Бесплатно. Сейчас деплой в Cloudflare делается руками, это и есть то, что надо автоматизировать.
3. **Зеркало Яндекс.** Object Storage с режимом сайта. Готовые файлы сборки копируются туда из GitHub Actions через `yc` или S3-совместимый инструмент. Ключи доступа в секретах GitHub, не в коде. Стоимость: рубли в месяц за хранение и трафик.
4. **Проверка.** Два раза в день Actions открывает оба зеркала и сверяет, что живы и одинаковы. При расхождении сообщение в Telegram.
5. **Посты в соцсети.** Тот же Actions при появлении нового отчёта в `main` отправляет пост в Telegram через бота. Бесплатно, без n8n.

### Домены (решение не принято)
- Вариант 1: `r9oof.com` на Cloudflare, `r9oof.ru` в Яндексе, ссылки друг на друга в подвале. Просто и бесплатно.
- Вариант 2: один домен, Cloudflare направляет посетителей по стране. Платная функция (Load Balancing), для статики перебор.
- Вариант 3: один домен, переключение в DNS руками при недоступности зеркала. Бесплатно, но требует вмешательства.

### Кэширование (добавлено 2026-10-05 по скрину «Caching Layers»)
- Заголовки кэширования на обоих зеркалах: картинки, стили, скрипты с долгим сроком и хешем в имени (Astro делает сам), HTML с коротким сроком.
- Яндекс-зеркало: рассмотреть Yandex Cloud CDN перед Object Storage; сравнить стоимость и скорость из регионов России.
- База логов: файл SQLite с версией или хешем в адресе, чтобы после обновления читатели не видели старую копию из кэша браузера.

### Безопасность (добавлено 2026-10-05 по скрину «10 Web Attacks»)
- Заголовки на обоих зеркалах: Content-Security-Policy, frame-ancestors (от кликджекинга), остальные по securityheaders.com.
- Секреты только в секретах GitHub и окружении; проверка перед коммитом на утечку ключей (gitleaks или аналог) в Actions.
- Формы и база с записью пока не планируются; при их появлении вернуться к CSRF, IDOR, ограничению частоты входа.

### Подводные камни
- Canonical и карта сайта должны вести на один главный адрес, иначе поисковики посчитают зеркала дублями. Яндексу главный `.ru`, Google главный `.com`; настраивается в Вебмастере и Search Console.

- Яндекс Облако требует оформленный аккаунт с привязанной картой, лучше российской.

- Как именно сейчас выкладывается сайт в Cloudflare (Pages или другой способ).
- Есть ли аккаунт в Яндекс Облаке и домен `.ru`.

## Ориентир процесса: AI-Native SDLC Playbook (Anthropic, 21.08.2026)

Записано 2026-10-04 как ориентир по просьбе владельца. Пересказ своими словами по открытому конспекту
(github.com/yibie/ai-native-sdlc-playbook); сам документ Anthropic отсюда не открывается, при случае сверить с первоисточником.

### Главная мысль
Код перестал быть узким местом. Затык переезжает в планирование, согласование, проверку безопасности,
тесты, приёмку и разбор инцидентов. Поэтому перестраивается процесс, а не инструменты.
Это цикл, а не конвейер: каждый этап заканчивается файлом в git, и этот файл — вход для следующего этапа.
История коммитов = история решений и аудит.

### Шесть этапов

| Этап | Артефакт в git | Агент делает | Человек делает | Как у R9OOF сейчас |
| --- | --- | --- | --- | --- |
| 1. План | `intent.md`: проблема, цели, ограничения | Помогает сформулировать | Автор идеи описывает, владелец одобряет | `docs/ideas.md`: решения с датами. Это и есть наш intent |
| 2. Дизайн | `spec.md`: требования и решение из intent | Пишет спецификацию, помечает проблемные места | Владелец утверждает | Разделы «База логов», «План по деплою»: варианты и выбор |
| 3. Сборка | `plan.md` (план реализации), код, `CLAUDE.md` (знания команды) | Claude Code в режиме плана; параллельные задачи в git worktrees | **План утверждается до кода, не после** | Ветка `TEST`. Сейчас запрет на код: ровно этот принцип |
| 4. Тест | Результаты тестов, набор проверок для настроек агента | Сам запускает тесты, видит результат, исправляет | Смотрит уже проверенный код | `npm run build` перед слиянием; чек-лист «20 пунктов»; claude-seo, security-audit-skill |
| 5. Деплой | PR с авторевью, `REVIEW.md` (правила ревью) | Первичное ревью: безопасность → соответствие правилам → логика | **Утверждает только человек** | План на два зеркала через GitHub Actions |
| 6. Поддержка | Новые `intent.md` из нарушенных метрик; проверка на каждый инцидент | Детектор отклонений (простая статистика), Claude для диагностики, откат через MCP | Смотрит результат, а не процесс | Проверка зеркал дважды в день, сообщения в Telegram |

### Минимальный набор для одного человека или маленькой команды
1. Папка `.claude/` в репозитории: `CLAUDE.md` (правила, команды сборки, типичные ошибки агента), `skills/` (правила и политики), `settings.json` (hooks и права).
2. Папка для intent-файлов с идеями.
3. Одна роль совмещает владельца, техлида и деплойщика. У нас так и есть.
4. Hooks вместо людей там, где можно: например, запрет агенту править тесты при исправлении ошибок; требование ссылки на задачу перед выкладкой в прод.
5. CI с проверками: при каждом изменении `CLAUDE.md` или скиллов прогонять набор реальных задач, чтобы агент не «сломался» от правки правил.
6. Петля обратной связи: агент сам запускает тесты и чинит, человек видит итог.

### Принципы, которые совпадают с нашими решениями
- Git — единственный источник правды.
- Сначала артефакт и решение, потом код.
- Человек утверждает, агент делает. Контроль не убирается, а встраивается в процесс так, чтобы его исполняла машина.

### Что взять, когда снимется запрет (обсудить)
- Оформлять задачи как intent → spec → plan: TODO из этого файла становится заданием для сборки без пересказа.
- Записать в `CLAUDE.md` типичные ошибки агента по итогам этой сессии (писал код без запроса).
- Hooks: как минимум запрет на правку файлов проекта вне ветки `TEST`.
- `REVIEW.md` с правилами проверки перед слиянием в `main`.

## База логов по локаторам и местам

Решение владельца 2026-10-04: база будет. Объём: около 20 000 связей сейчас, прибавка около 1000 в месяц.

### Что должна уметь (предварительно, уточнить)
- Проверка локатора корреспондента по QRZ.com и qrz.ru (как в скилле adif-fix), сверка локатора с QTH.
- Собственные выезды: район RDA, локатор, координаты.
- На сайте: карта связей, статистика по районам и диапазонам, поиск «есть ли связь со мной».

### Варианты
1. **Файлы в git.** ADIF/CSV/JSON в репозитории, страницы и карты собираются при сборке. Проверка локаторов заранее, скриптом. Сервера нет, история в git, вписывается в два зеркала. Поиска «на лету» нет.
2. **База внутри сайта.** Логи в одном файле SQLite на сайте, браузер читает его сам (sql.js или DuckDB-Wasm). Поиск и фильтры у читателя, сервер не нужен. При 20 000 связей файл около 2–4 МБ, терпимо; при росте по 1000 в месяц через 5 лет около 80 000 связей и 10–15 МБ, ещё приемлемо.
3. **База с сервером.** Supabase (облако, зарубежные серверы, из России нестабильно), своя установка Supabase или Postgres в Яндекс Облаке (через Coolify), Yandex Managed PostgreSQL (платно). Нужна только если посетители будут что-то отправлять: подтверждения, запросы QSL, кабинеты.

### Предварительный выбор
При 20 000 связей, +1000 в месяц и только поиске со стороны посетителя: **вариант 2** (SQLite в браузере). Вариант 3 не нужен. Окончательно решает владелец.

### Пометка по запросам (добавлено 2026-10-05)
- Индексы в SQLite по полям CALL (поиск «есть ли связь со мной») и QSO_DATE (поиск по дате).
- Статистика «самые частые» (корреспонденты, районы, страны) обычным запросом с сортировкой и LIMIT, без своего кода.
- Несколько ADIF с одного выезда сливаются в один период активации по датам.
- (2026-10-05) Проверка локаторов: один словарь «позывной → локатор, место», каждый позывной к QRZ и геокодеру ходит один раз, повторы берутся из словаря. Дубли при слиянии ADIF ловятся по ключу «позывной + дата + время + диапазон», а не сравнением каждой записи с каждой.

### Инструменты для проверки локаторов
- QRZ.com XML API: платная подписка XML Logbook Data. qrz.ru: API нет, только страницы.
- HamDB, HamQTH: бесплатные справочники позывных с API, слабее QRZ.
- Геокодер для сверки локатора с QTH: Яндекс Геокодер (бесплатный лимит), Nominatim от OpenStreetMap (бесплатно, ограничение по частоте).
- Расчёт локатора по координатам и расстояний: простая формула, библиотек много.
- Club Log, LoTW, eQSL: подтверждения связей, если показывать на сайте.

### Ответы владельца 2026-10-04
- Посетитель только проверяет свою связь (поиск по позывному), ничего не отправляет. Значит, сервер и запись в базу не нужны: вариант 2 (SQLite в браузере) подходит полностью.
- Подписка QRZ.com XML есть. Проверка позывных через QRZ XML API, HamDB и HamQTH как запасные.
- Логи берутся из N1MM Logger+ (экспорт ADIF) и вручную (ADIF). N1MM экспортирует ADIF стандартно, значит обновление базы при сборке сайта можно автоматизировать: положил ADIF в репозиторий, остальное делает сборка. Ручные ADIF идут тем же путём.
