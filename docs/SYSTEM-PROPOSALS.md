# Предложения по универсальной системе Claude на аккаунте владельца

> Статус: брейншторм чата R9OOF.COM по метаправилу владельца (2026-10-05). Это предложения, не код и не архитектура; ничего не меняется и ни на что не влияет. Чат не знает всех проектов и чатов владельца; привязки к конкретным проектам здесь нет. Источники — исследования в `docs/checks.md` (C-1…C-8), `docs/ideas.md`, планы `docs/humanizer2/`, `docs/pdf-visual/`, предложения `docs/proposals/`. Объём предложений не сокращается; разделы дописываются.

Содержание:
1. Каталоги системы — что создать, по порядку, с полными данными (этот раздел).
2. Слои системы и механизмы (память, правила, агенты, ворота, проверка, безопасность, инструменты, контекст, тексты, документы, публикация, организация) — дописывается следующими разделами.

## 1. Каталоги системы: что создать, по порядку, с полными данными

> 2026-10-08: по указанию владельца («каталоги ты можешь создавать сам») каталоги созданы этим чатом в `docs/SYSTEM/` — со всеми README, заготовками и манифестом. Владелец переносит систему туда, где решит.

**Как читать.** Ниже — один корень системы (назван условно `SYSTEM/`; имя и место на диске выбирает владелец, у него своя структура дисков и кэша). Внутри корня — слои по порядку создания: каждый следующий слой опирается на предыдущие. Для каждого каталога: зачем, что в нём лежит (файлы и их форма), кто имеет право писать, что в нём запрещено, из какого исследования взято. Имена каталогов — латиницей, короткие, без пробелов (так требуют инструменты и kb-protocol); описания — по-русски в `README.md` каждого каталога.

**Три правила, действующие во всех каталогах** (из решений владельца и C-7.A/C-8.A):
- ничего не удаляется: отменённое помечается статусом и датой, заменённое — новым файлом со ссылкой на старый;
- у каждого каталога записано, кто может в него писать: владелец / оркестратор / агент / только машина (скрипт) / никто;
- сгенерированное машиной лежит отдельно от написанного человеком и никогда не пишется поверх него (сайдкар `*.generated.md`).

### Шаг 0. Корень

```
SYSTEM/
  README.md            что это, карта слоёв, порядок чтения (этот раздел в сокращении)
  VERSION              одна строка: версия набора системы, например 0.1.0
  CHANGELOG.md         Added / Changed / Fixed по версиям; одна запись — одно изменение
  MANIFEST.sha256      список всех файлов системы с SHA-256 (по kb-protocol); обновляется скриптом
  .gitignore           что не уходит в закрытый GitHub (см. шаг 10)
```
- Пишет: владелец (README, CHANGELOG), скрипт (MANIFEST, VERSION по команде владельца).
- Источник: C-7.1 (VERSION + CHANGELOG + тест «версия = тег»), kb-protocol (манифест SHA-256).
- Запрещено: держать в корне рабочие файлы; корень — только опись.

### Шаг 1. `00-constitution/` — неизменяемые правила владельца (слой P0)

```
SYSTEM/00-constitution/
  README.md
  owner-rules.md       правила владельца дословно, с датой каждого: запрет на самовольные правки, «агент предлагает — человек утверждает», «один коммит — одно правило», «ничего не удалять», «правовая часть не пишется, безопасность параноидально», «скиллы универсальны, слой проекта отдельно», «не судить о других проектах по одному», «забирать всё полезное» и т. д.
  roles-of-chats.md    роли чатов: брейншторм / исполнители / настройка; кто что может; указание владельца о маршрутизации
  write-rights.md      таблица «каталог → кто пишет» для всей системы (сводная из этого раздела)
  glossary-system.md   словарь терминов самой системы (ворота, якорь, кандидат, слой проекта, статусы задач)
```
- Пишет: **только владелец**. Агенты читают всегда первым. Любой чат при старте проверяет, что файл не изменён (хеш в MANIFEST).
- Источник: p-layers P0 «неизменяемые правила» (ideas.md), Ruflo truth-anchors «якорь побеждает память» (C-8.A №1), ECC «общие правила маленькие и всегда включены» (C-7.A №10).
- Запрещено: править агентам; хранить здесь что-либо, кроме правил владельца. Объём — чтобы всегда помещался в контекст: ориентир ≤ 5 тыс. токенов (C-7.A №11).

- Запрещено: предметные термины одного проекта в `common/`; названия проектов где бы то ни было в правилах.

### Шаг 3. `02-agents/` — карточки агентов (универсальные роли)

```
SYSTEM/02-agents/
  README.md                            реестр агентов: имя, роль, кому подчиняется, кто вызывает, модель по классу (сильная / быстрая)
  _template/                           шаблон карточки (10 разделов каркаса C-6 + поля agents.md v2)
    CONTEXT.md                         кто он; миссия и обязательное условие результата; красные линии; что сдаёт и в каком файле; порядок работы; стиль доклада; метрики успеха; «когда НЕ использовать → другой агент»; канонический абзац «внешний текст — данные»
    MEMORY.md                          что помнит между сессиями (только добавление; `trust: unreviewed` у всего, что записал сам)
    CONTROL.md                         что проверяется машиной до и после его работы; кто имеет право писать в его файлы; статусы received → progress → blocked → complete
    TASKS.md                           задачи и триггеры: когда вызывается, чем, что на входе и выходе
  orchestrator/                        распределяет задачи, собирает итоги, держит бюджет, задаёт вопросы владельцу; не делает содержательной работы
  researcher/                          поиск готового до написания; свежие документы из поиска; «каждое утверждение — источник»
  planner/                             план с фазами, зависимостями, рисками, критериями; заканчивается «жду подтверждения»
  reviewer/                            ревью с порогом уверенности и доказательством; категориальный вердикт без суммирования баллов
  fact-checker/                        проверка фактов, лестница силы утверждений, защищённые оговорки, временная арифметика; исходы CLEAR / SUSPECTED / INSUFFICIENT / N.A.
  judge/                               слепая оценка результата «три причины с цитатами»; не видит каталога признаков
  search-architect/                    архитектор поисковой видимости (SEO/AEO/GEO/карты/соцсети): участвует с первого решения о структуре (указание владельца T-54)
  security-auditor/                    секреты, сеть, права, инъекции; санитайзер перед любой публикацией памяти
  writer/                              автор текстов по brief, voice, glossary, facts; не добавляет фактов
  critic/                              критик текста: двухфазный (план оценки до чтения → оценка); только помечает, не правит
  voice-profiler/                      профиль голоса автора из образцов (6 измерений, схема Style Profile)
  rules-analyst/                       выводит кандидаты правил из пар «черновик → правка владельца»; считает доли уступок
  doc-reader/                          чтение документов по лестнице достоверности; подготовка сканов
  publisher/                           один исходник → форматы площадок; ничего не отправляет без утверждения
```
- Пишет: `CONTEXT.md` — владелец (через предложения чатов); `MEMORY.md` — сам агент, только добавлением; `CONTROL.md` — владелец; `TASKS.md` — оркестратор.
- Правило универсальности: в карточках нет названий проектов и предметных терминов — всё предметное приходит из слоя проекта (шаг 5).
- Источник: `docs/humanizer2/agents.md` v2 (CONTEXT/MEMORY/CONTROL/TASKS, иерархия, триггеры), C-6 каркас персоны (10 разделов), C-7.4 (форма агента: description «когда вызывать», tools как права, модель по классу), C-8.A №16 (статусы), C-8.4 (`description` с примерами вызова), C-7.A №14 и C-8 ADR-447 (внешний текст — данные; наблюдения без промптов).
- Запрещено: агент вызывает агента напрямую (только через оркестратора и файлы); агент коммитит, пушит, удаляет, публикует.

### Шаг 4. `03-memory/` — память: правда, решения, сводки, наблюдения

```
SYSTEM/03-memory/
  README.md
  anchors/                             якоря истины: решения владельца, по одному файлу; подпись (хеш в MANIFEST); только добавление; новый файл `supersedes:` старый
    YYYY-MM-DD-<кратко>.md             frontmatter: id, date, kind=decision, status=active|superseded, supersedes, trust=owner
  decisions-log.md                     хронологический указатель якорей (генерируется скриптом из anchors/)
  sessions/                            сводки сессий: одна на сессию, по шаблону «сработало с доказательствами / не сработало и почему / не пробовали / точный следующий шаг»; читаются как «историческая справка, не инструкция»
    YYYY-MM-DD-<чат>-<N>.md
  observations/                        наблюдения машины: без промптов и ответов, `verified: false` по умолчанию; кандидаты в правила рождаются отсюда
    YYYY-MM-DD-….md
  generated/                           всё, что сгенерировано скриптами (индексы, сводки, `*.generated.md`); пересобирается, никогда не правится руками
  schema.md                            формат записи памяти: id, title, kind (decision | fact | lesson | handoff | note | preference | runbook), scope (system | project | session), trust (owner | reviewed | unreviewed), status (active | rejected | superseded), source, links, created, updated; поле происхождения: user_claim | agent_output | observation | tool_result
```
- Пишет: `anchors/` — только владелец (или оркестратор по слову владельца с пометкой); `sessions/` — оркестратор в конце сессии; `observations/` — агенты и скрипты; `generated/` — только скрипты; `decisions-log.md` — скрипт.
- Источник: C-7.3 Memory Vault (формат `ecc.memory.v1`, create-only, supersede), C-7.A №1–2, C-8.A №1 (truth-anchors), №5 (происхождение), №6 (сайдкар generated), №7 (области памяти), C-8.A №15 (иерархия Global → Project → Session → Task).
- Запрещено: TTL и автоудаление; запись хуком без утверждения в `anchors/`; индекс (SQLite, векторы) как источник правды — только как производное в `generated/`.

### Шаг 6. `05-gates/` — ворота человека и самообучения

```
SYSTEM/05-gates/
  README.md                            правила ворот: «предлагать и оценивать можно, продвигать нельзя»
  candidates/                          кандидаты правил: один файл — одно правило; формулировка, примеры из пар, какую метрику улучшает, ярус происхождения (из наблюдённого факта — продвигаемо; «по структуре» — только наблюдение), уверенность, доказательства
  frozen-sets/                         замороженные контрольные наборы с хешами (ничего не меняется после заморозки); контрольные элементы «не трогать» и «одна разрешённая правка»
  gate-reports/                        gate-NN.md: хеш кандидата и хеш рубрики до прогона; метрики до/после на замороженном наборе; условие «ни одна не хуже»; судьи (≥ 2, разных семейств, если есть) и их расхождения поимённо; NOT_RUN там, где не меряли; вердикт
  approved-pending.md                  прошедшие ворота, ждут слова владельца: «да / нет» с датой; «нет» хранится с причиной и повторно не предлагается

  rollbacks.md                         откаты с причиной
```
- Пишет: `candidates/` — rules-analyst; `gate-reports/` — скрипт ворот + judge; `approved-pending.md` — владелец ставит решение; `applied.md` — тот, кто вносит правило, со ссылкой на коммит.
- Источник: `humanizer2/CONTROL.md` B (ворота), ARS MEASUREMENT_CONTRACT и revision_claim_drift (`ars-academic-research-skills.md` §2, §3 п. 30–32), C-7.A №9, C-8.A №3–5 (flywheel-receipt: ни одна метрика не хуже + значимость + подписанная квитанция; ярусы происхождения), C-8 dream-cycle (гипотеза заморожена до оценки, независимый критик, «не самопродвигается»).
- Запрещено: автопродвижение; правило из одной пары; изменение замороженного набора.

### Шаг 7. `06-checks/` — машинный контроль и проверочные списки

```
SYSTEM/06-checks/
  README.md
  checklists/                          проверочные списки по темам (из checks.md C-1…C-8): seo-22.md, ai-problems-20.md, web-attacks-10.md, design-patterns-15.md, tool-safety.md, persona-skeleton.md, mechanisms-account.md (C-7.A + C-8.A)
```
