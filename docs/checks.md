Общий файл. Чат R9OOF.COM заносит сюда списки из разобранных скринов с предварительной оценкой. Другие чаты (сайт, деплой, humanizer, база логов, «Настройка Claude») проверяют по своей части и заполняют колонки «Проверено» и «Решение». Строки не удалять.

Колонки: пункт · предварительно по состоянию кода в `TEST` · надо ли нам · кто проверяет · проверено (дата, чем) · решение.

## C-4 · «15 шаблонов проектирования» (скрин 2026-10-05) — для всех проектов

Это классические шаблоны программирования (книга «банды четырёх»), а не инструменты. Проверка здесь другая: не «есть или нет», а «какой шаблон уже лежит в основе наших планов и где его стоит назвать явно», чтобы проекты-исполнители строили одинаково. Предварительная карта от чата R9OOF.COM; исполнители подтверждают или заменяют.

| № | Шаблон | Суть | Где у нас уже так | Надо назвать явно? | Проверяет | Проверено | Решение |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | Одиночка (Singleton) | один общий экземпляр | одна память проекта (`ideas.md`, папки на `T:`), один источник правды в git | да: «один стор памяти, не копии» | Настройка Claude | | |
| 2 | Фабричный метод | кто-то решает, какой объект создать | Оркестратор выбирает набор агентов и режим по жанру из `brief.md` | да, в контексте Оркестратора | humanizer | | |
| 3 | Строитель (Builder) | объект собирается по шагам | `brief.md` собирается из жанра, голоса, длины, ограничений; отчёт собирается из `facts.md` + `voice.md` | нет, достаточно схем файлов | humanizer | | |
| 4 | Адаптер | подогнать один формат под другой | импорт ADIF из N1MM и вручную в единую базу; экспорт сборки в формат Яндекс Object Storage | да: один адаптер на формат, в базе логов | база логов, деплой | | |
| 5 | Декоратор | обернуть, добавив поведение, не меняя суть | жанровые флаги сканера (`--genre`) поверх базовых правил; профиль голоса поверх общих правил жанра | нет | humanizer | | |
| 6 | Фасад | простой вход в сложную подсистему | Оркестратор как единственный вход для владельца; шлюз MCP перед серверами | да, в предложении MCP | Настройка Claude | | |
| 7 | Заместитель (Proxy) | контроль доступа к объекту | MCP-сервер как контроль прав на данные; серверу доверяют, хосту нет | да, в видении хост/сервер | Настройка Claude | | |
| 8 | Компоновщик | части и целое одинаково | `TODO.md` общий, планы проектов внутри с той же структурой (PLAN/MEMORY/CONTROL) | уже так | этот чат | | |
| 9 | Наблюдатель | оповестить всех при изменении | триггеры: вебхуки GitHub → Actions → Telegram; таблица триггеров агентов | да, в деплое и у Оркестратора | деплой, humanizer | | |
| 10 | Стратегия | сменить алгоритм на ходу | лёгкий / полный режим; выбор профиля голоса; выбор домена для зеркала | да, у Оркестратора | humanizer | | |
| 11 | Команда | запрос как объект, с отменой | обмен файлами между агентами (`draft-N.md`, `blocked.md`); откат одним коммитом | да: «запрос — это файл, отмена — коммит» | humanizer | | |
| 12 | Итератор | обход без знания внутренностей | прогон контрольного набора воротами; обход страниц сайта сканерами | нет | humanizer | | |
| 13 | Состояние | поведение зависит от состояния | статусы задач в `TODO.md` (ожидает → в работе → на проверке → сделано); статусы правил (кандидат → ворота → утверждено) | уже так | этот чат | | |
| 14 | Шаблонный метод | жёсткий каркас, свои шаги | у каждого агента одинаковый каркас (CONTEXT, MEMORY, CONTROL, TASKS) и свои задачи; у каждого плана PLAN/MEMORY/CONTROL | уже так | все | | |
| 15 | Цепочка обязанностей | запрос идёт по цепочке обработчиков | Автор → Критик → Проверяющий → Судья, каждый пропускает или возвращает | да, в контекстах агентов | humanizer | | |

Итог: 10 из 15 шаблонов уже лежат в основе планов. Явно назвать стоит семь: Одиночка (память), Фабрика и Стратегия (Оркестратор), Адаптер (форматы логов), Фасад и Заместитель (MCP), Наблюдатель (триггеры), Команда (файлы и откат), Цепочка (контроль). Не нужны как отдельные решения: Строитель, Декоратор, Итератор.
