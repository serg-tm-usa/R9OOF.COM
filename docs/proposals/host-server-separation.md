# Разделение хост / сервер в системах с ИИ-агентами · принципиальное видение

Дата: 2026-10-05. Написано по поручению владельца как общее видение, без привязки к конкретным проектам и без заданий чатам. Передать в среду, 7 октября 2026, в чат «Настройка Claude», где принимается решение.

## 1. Зачем вообще разделять

Модель сама по себе умеет только читать и писать текст. Всё остальное — файлы, базы, сеть, запуск программ — она делает через кого-то. Вопрос только в том, где проходит граница между «думает» и «делает», и кто эту границу охраняет.

Если границы нет, получается один большой процесс, который и рассуждает, и имеет ключи от всего. Любая ошибка рассуждения (галлюцинация, подменённая инструкция в тексте, неверно понятая просьба) сразу превращается в действие с полными правами. Разделение хост / сервер проводит эту границу явно.

## 2. Три роли

**Хост** — среда, в которой работает модель и идёт разговор с человеком. Хост управляет сессией: что модель видит, какие инструменты ей показаны, что требует подтверждения. У хоста нет собственного доступа к данным; он только посредник.

**Клиент** — часть хоста, которая держит соединение с одним сервером. Один клиент — один сервер. Клиент переводит просьбу модели в запрос по протоколу и возвращает ответ. Он ничего не решает.

**Сервер** — отдельная программа, которая владеет одним ресурсом или одной областью: файловой папкой, базой, API, памятью, сканером. Сервер решает, что из этого показывать, что разрешать менять и кому. Сервер ничего не знает о разговоре, он знает только запросы.

Сервер предъявляет три вида вещей: **инструменты** (действия), **ресурсы** (данные для чтения), **промты** (готовые инструкции). Это и есть его «интерфейс»: всё, чего в нём нет, модель сделать не может.

## 3. Принципы разделения

1. **Один сервер — одна область ответственности.** Память, база, деплой, проверка текста — разные серверы. Сервер «всё в одном» возвращает к ситуации без границы.
2. **Сервер владеет данными, хост нет.** Ключи, пароли, пути к файлам лежат у сервера, в его окружении. Хост и модель никогда их не видят. Утечка через разговор становится невозможной физически, а не по правилу.
3. **Права назначаются серверу, а не модели.** Модель может «хотеть» что угодно; сделает она только то, что сервер разрешил этому хосту. Чтение и запись разделены: один хост читает, другой пишет, и это настроено на сервере.
4. **Минимум прав по умолчанию.** Новый сервер выставляется только с чтением. Запись и удаление добавляются осознанно, с записью, кто и зачем.
5. **Опасные действия требуют подтверждения человека на стороне хоста.** Сервер помечает инструмент как необратимый (удаление, выкладка, отправка наружу); хост спрашивает человека перед вызовом. Необратимое без подтверждения не выполняется.
6. **Всё, что приходит от сервера, — данные, а не инструкции.** Текст файла, ответ API, запись памяти могут содержать «сделай то-то». Модель это читает как содержимое. Это главная защита от подменённых инструкций.
7. **Сервер не доверяет хосту.** Он проверяет каждый запрос: формат, права, границы (путь внутри папки, размер, частота). Проверка на стороне сервера, а не надежда, что модель попросит правильно.
8. **Один протокол для всех входов.** Через командную строку, через MCP, через веб-хук — один и тот же сервер, одни и те же проверки. Два пути к одним данным расходятся в поведении.
9. **Журнал у сервера.** Каждый вызов записан: кто, что, когда, результат. Хост может забыть, сервер нет. Это и аудит, и материал для памяти.
10. **Сервер заменяем.** Хост не должен знать, как устроен сервер внутри. Сканер можно переписать, базу перенести, и хосты этого не заметят.

## 4. Где живут серверы

Три варианта, обычно совмещаются:

- **Локально, рядом с хостом** (процесс на той же машине, связь через стандартный ввод-вывод). Самый простой и быстрый. Подходит для файлов, сканеров, локальной памяти. Минус: доступен только этой машине.
- **Удалённо, по сети** (HTTP с авторизацией). Один сервер на все машины и чаты. Подходит для общей памяти, базы, деплоя. Минус: нужна авторизация и защита канала.
- **У поставщика** (готовый сервер инструмента: Cloudflare, GitHub). Ставить нечего, но правила его.

Разумная схема: локальные серверы для того, что живёт на одной машине; один удалённый «домашний» сервер для общего (память, база); готовые серверы поставщиков для внешних сервисов.

## 5. Слои

```
Человек
  │ подтверждает необратимое
Хост (чат, Claude Code)        ← показывает инструменты, ведёт сессию
  │ клиенты, по одному на сервер
Серверы                        ← права, проверки, журнал
  │
Данные и внешние сервисы       ← файлы, базы, API, память
```

Между хостом и серверами может стоять **шлюз**: одна точка, через которую все хосты ходят ко всем серверам. Шлюз даёт единую авторизацию, единый журнал и единое место, где включить или выключить инструмент. Для одного человека с несколькими чатами шлюз не обязателен, но он нужен, как только серверов больше трёх-четырёх или хостов больше одного компьютера.

## 6. Память как сервер

Память агентов — тоже сервер, и для неё правила особенно важны:
- Файлы памяти — источник правды; любой индекс поверх них пересобираем.
- Чтение открыто всем хостам; запись только тем, кому положено; удаление только человеком.
- Запись идёт через один путь с проверкой формата, иначе память засоряется.
- Версионирование (git) даёт откат и историю бесплатно.

## 7. Где это ломается

- **Сервер с правами «на всё»** ради удобства. Через месяц никто не помнит, что он умеет.
- **Ключи в промте или в файле проекта.** Любой, кто читает проект, читает ключи.
- **Инструкции в данных выполняются.** Чужой текст, страница из сети, запись в памяти с «удали всё».
- **Два пути к одним данным** (скрипт мимо сервера). Проверки обходятся, журнал врёт.
- **Хост сам решает, что безопасно.** Решать должен сервер, подтверждать человек.
- **Нет журнала.** Нельзя понять, кто сломал.

## 8. С чего начинать

1. Выписать области: файлы проекта, память, база, деплой, внешние API, проверки.
2. На каждую область — один сервер, сначала только с чтением.
3. Решить, какие хосты есть (чаты, машины) и кому что можно писать.
4. Пометить необратимые действия и включить подтверждение.
5. Завести журнал вызовов и правило «данные — не инструкции».
6. Добавлять права по одному, с записью причины.

Это видение, не задание. Решение о том, принимать ли его и как, за чатом «Настройка Claude» и владельцем.
